# Drizzle Migrations

## Purpose

This directory holds SQL migration files generated by Drizzle and the metadata chain (`_journal.json` + `meta/` snapshots) that describes schema evolution. Treat both together as an atomic unit: migrations cannot be applied without their journal entries, and the journal cannot be trusted without corresponding snapshots.

## How Drizzle Tracks State

- **`_journal.json`** — Ordered journal of all applied migrations. Each entry has `{ idx, tag, when, version }`. The `idx` is a sequence number (not the filename); Drizzle uses it to determine the next index.
- **`meta/XXXX_snapshot.json`** — Schema snapshot after migration `idx:XXXX`. Files chain via `prevId` references (each snapshot knows its predecessor).
- **Generation process** — `pnpm db:generate` reads the latest journal entry's snapshot, diffs it against `lib/db/schema.ts`, and emits a new `.sql` file + snapshot with the next available `idx`.
- **Migration numbering is derived from `idx`, NOT filenames on disk** — A file named `0030_foo.sql` could have `idx: 31` if two migrations were inserted retroactively.

## The Journal Gap (idx 25 → 28)

**Context**: In March 2026, two migrations were hand-written and applied directly to production out-of-band:
- `0026_add_sandbox_guardrails.sql` (added guardrails columns to sandbox tables)
- `0027_add_table_comments_and_fk_indexes.sql` (added schema comments and optimized foreign-key indexes)

These were **intentionally NOT added to `_journal.json`** because adding them retroactively would cause Drizzle to attempt re-applying already-applied SQL on production, breaking the deployment. Drizzle detects applied migrations by matching the journal index; if a migration is in the journal but already applied to the DB, it will still attempt to re-run it, causing duplicate-constraint and other errors.

**The gap consequences**:
- Journal has `idx: 25` (rate limit indexes), then jumps to `idx: 28` (Phase 0 Task 3 — sandbox tables).
- `idx: 26` and `idx: 27` are **permanently absent from the journal**.
- The corresponding SQL files (`0026_*` and `0027_*`) remain on disk but are marked as "hand-applied" (not managed by Drizzle).
- The missing snapshots mean the schema state from indices 26–27 is not recorded in metadata.

**Critical**: Do **NOT** attempt to "fix" the gap by retroactively adding 26 and 27 to the journal. This will break production deployments.

## How to Add a New Migration Safely

1. **Modify `lib/db/schema.ts`** — Update table definitions (add columns, change types, etc.).
2. **Run `pnpm db:generate`** — Drizzle reads the last journal entry's snapshot, diffs against schema, and writes:
   - A new `.sql` file (e.g., `0030_xxx.sql` if the last idx was 29)
   - A new `meta/0030_snapshot.json` file
   - A new journal entry with `idx: 30`
3. **Verify the generated SQL** — Open `0030_xxx.sql` and check that it matches your intent. Watch for spurious ALTER statements or unexpected columns that indicate snapshot drift.
4. **If Drizzle produces spurious changes** — The snapshot is drifted. See "Snapshot drift repair" below before committing.
5. **DO NOT rename files manually** — Drizzle manages filenames. If a collision occurs (e.g., on a stale branch), see "Filename collisions" below.
6. **Run migrations locally** (optional, for testing):
   ```bash
   cp .env.local .env
   DOTENV_CONFIG_PATH=.env pnpm tsx -r dotenv/config node_modules/drizzle-kit/bin.cjs migrate
   rm .env
   ```
7. **Commit all three together** — SQL file + snapshot + journal entry in one commit. Never commit one without the others.

## Snapshot Drift Repair

If `meta/XXXX_snapshot.json` is out of sync with the live database (e.g., someone applied a hand-written SQL change without updating the snapshot), Drizzle will generate spurious changes on the next `pnpm db:generate`.

**To repair**:
1. Manually edit the most recent `meta/` snapshot to match the current database schema state.
2. Re-run `pnpm db:generate` — it should now diff correctly.
3. Commit the repaired snapshot + new migration together.

**Example**: Commit `3a7b425` (Phase 0 Task 3) repaired snapshot drift for the `heartbeat_extension_count` column by manually updating the snapshot, then regenerating the next migration.

## Filename Collisions

If `pnpm db:generate` produces a file named `0026_foo.sql` on a branch where `0026_bar.sql` (from a different branch) already exists, you must manually resolve the collision:

1. `git mv 0026_foo.sql 0028_foo.sql` (rename to next available index).
2. `git mv meta/0026_snapshot.json meta/0028_snapshot.json` (rename snapshot to match).
3. Update `_journal.json` — change the `tag` field of the new entry from `"0026_foo"` to `"0028_foo"`.
4. Commit the rename together with the updated journal.

**Example**: Commit `7f2e173` (Phase 0 Task 3 renumber) renamed a generated migration from `0026` to `0028` after detecting a collision with an out-of-band migration.

## Static-Logging and Safety

Migrations run with full database privileges. **Do not add data-migration steps that log user-identifying values.** SQL-only schema changes (CREATE TABLE, ALTER TABLE, ADD COLUMN, CREATE INDEX) are safest. If you must include data migrations, log only static messages (e.g., `'Migration completed'`) and avoid logging user IDs, emails, or row counts.
